# web/ — the demo app + extraction scripts

The upstream OrcaSlicer sources live in `../slicers/slicer/`, and the reverse-engineered kernel, SDK and components live in `../packages/`
(with zero build or runtime dependency on `../slicers/slicer/`). Guide: [`GUIDE.md`](GUIDE.md), specs: [`SPECS.md`](SPECS.md).

## Structure

The npm workspaces root is the **repository root** `package.json` (`packages/*` + `web/viewer`) — a single `npm i` at the root installs everything.
- **`../packages/engine/`** — `three-slicer`: the WASM slicing kernel SDK. The public API + worker + settings mapping.
  - Rebuilding the kernel (`../packages/wasm-core/build.sh`) became **fully standalone in stage 34**: the upstream deps (clipper, clipper2, libnest2d, libigl,
    admesh, … all 23M of deps_src) were copied into `wasm-core/third_party/` -> the build succeeds without `slicer/` (demonstrated: build.sh plus 12 suites green
    while slicer was temporarily renamed). Golden byte-identity is preserved.
- **`../packages/data/`** — `three-slicer/data`: the extracted artifacts (config-schema/ui-tree/toggle-rules/invalidation-map/preset-keys, plus the printer/process/filament preset catalogs), regenerated by `extract_all.py`.
- **`../viewer-package/src/components/`** — `three-slicer-viewer/components` (MIT): the React settings form, taking its data as props; `three-slicer/components` (`../packages/components/`) wraps it with upstream's schema and rules (props-driven, zero global/context coupling, Shadow DOM). Provides `<SettingsPanel/>` (usage: `packages/components/README.md`).
- **`../packages/viewer/`** — `three-slicer/viewer`: the `<Viewport/>` viewer component (three.js, Shadow DOM).
- **`viewer/`** — the demo app. Consumes engine (worker, settings) + data + components + viewer as workspaces.

### Using `three-slicer` (headless/Node)

```js
import { createSlicer } from 'three-slicer'        // example: packages/engine/examples/headless.mjs

const slicer = await createSlicer()                    // loads the WASM kernel
// Batch: the whole result (gcode + stats + layers)
const r = slicer.slice(stlArrayBuffer, kernelParams)
console.log(r.stats.layers, r.gcode.length)
// Streaming (stage-30 OOM tolerance): emits each layer and frees the heap; the result carries stats only
slicer.slice(stlArrayBuffer, kernelParams, {
  onProgress: (done, total) => {},
  onLayer: ({ z, idx, gcode, paths, widths }) => { /* accumulate for GPU upload / download */ },
})
slicer.dispose()
```

In the browser (off the main thread) use a worker — under a bundler `createSlicerClient()` from `three-slicer/client` creates one
that Vite/webpack emit correctly; without a bundler, `new Worker(engineWorkerURL(), { type: 'module' })`. Either way the worker speaks
the stage-30 streaming protocol (`{type:'layer'|'done'|'error'|'progress'}`). Converting UI settings into kernel parameters is
`deriveKernelParams(settings)` from `three-slicer/settings` (schema-driven, for bundlers/browsers).

## Usage (in a web implementation)

- **Automatic settings form generation**: join `config-schema.json` + `ui-tree.json`. The widget selection rules are in guide §4.3.
- **Enable/disable**: the `enable_if` in `toggle-rules.json` is raw C++. It can be translated mechanically, e.g. `config->opt_bool("x")` ->
  `cfg.x`, `opt_enum<T>(...) == T::y` -> `cfg.x === 'y'`. Inline the variables from `locals`
  first.
- **Incremental slicing**: use `invalidation-map.json` to decide which steps a changed option re-runs.

## Known limitations

- The extraction is regex-based and static. **The build-based dump tool (guide §11.1) was realized in stage 11** ->
  `config-schema-builddump.json` (817 entries dumped from the real `print_config_def` in WASM, backed by the compiler).
  The cross-check (`compare_schema.mjs`) found 0 type mismatches, broadly confirming the accuracy of the regex extraction;
  the differences were mostly the regex over-including (107 entries from separate CLI/placeholder ConfigDefs), under-including (17 loop-generated) or representational.
  For UI consumption keep using `config-schema.json` (it is richer in UI metadata: categories, tooltips, line numbers), but trust the build dump as
  the final truth about which options exist and their types and defaults.
- The **automatic value-correction dialog rules** in `update_print_fff_config` (ConfigManipulation.cpp) — e.g. forcing wall_loops=1 when spiral
  mode is on — are not toggles, so they are absent from this JSON. They must be translated by hand.
- The SLA family is extracted and now consumed: the SLA tabs render in the settings panel and `deriveSlaParams`
  reads the display/support/pad keys (see `packages/engine/README.md`, "SLA parameters").
- The ui-tree <-> schema cross-check once found 2 dangling references (`spaghetti_detector`, `pad_edge_radius`);
  the current artifacts carry neither — the cross-check now reports zero.

## Viewer

- Location: `web/viewer/` (Vite + React 18 + react-router v7 + three.js). It consumes the published package surface
  by its workspace name — `three-slicer/viewer`'s `<Viewport/>` and `three-slicer/components`' `<SettingsPanel/>` —
  rather than importing package source files or raw JSON.
- Run: one `npm i` at the repo root, then `cd web && make dev` (rebuilds the package dist and the bundled demos,
  then starts Vite with browser routing).
- Routes: `/` is a crawlable landing page, `/slice` is the slicer, `/demos` hosts the built `examples/` demos, and
  `/testbed` is a scratch page. The old deep-link routes (`/tab/:builder`, `/option/:key`, `/search`) are gone.
- The slicer screen is the packaged `<Viewport/>` (desktop-style shell: top bar, gizmo rail, sidebar cards) sharing
  one sparse settings map with `<SettingsPanel/>`; everything in `viewer-package/VIEWER.md` applies — model import
  (STL/OBJ/3MF project/AMF/PLY, STEP via the demo's `step_loader.js` on `registerLoader`), multi-plate, painting,
  undo/redo, the GPU volumetric toolpath preview, move scrub, G-code/3mf/preset export, and the SLA route (resin
  card, support/pad preview, `.sl1` export and import).
- Toggle rules are applied: the panel greys out options whose `enable_if` evaluates false (`three-slicer/toggle`).
- How each piece came to be — the volumetric renderer's libvgcode port, the coordinate-frame fix, the SLA chain —
  is the stage-by-stage log in [HISTORY.md](HISTORY.md).
